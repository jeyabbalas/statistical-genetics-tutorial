The tools: PLINK, R packages, GrafAnc and friends

The practical runs about twenty commands with three programs. PLINK 1.9 reads the genotype files and computes every quality-control statistic. R reads the text tables that PLINK writes and turns them into histograms, scatter plots and counts. GrafAnc places each person relative to a set of reference populations and assigns a genetic ancestry group. A shell starts all three, and git, conda, Homebrew or Docker install them. This page explains each tool: what it is for, how it works inside, what it reads and writes, and the exact flags and functions the practical uses.

Mental model

Programs pass files: PLINK writes tables, R reads them, GrafAnc adds one more

Every tool in the practical reads files and writes files. PLINK turns a genotype fileset into report tables and new filesets, R turns report tables into plots and counts, and GrafAnc turns a fileset into a table of ancestry scores. The shell starts every program, and three folder variables decide where each file lives.

  • The shell runs every command. A command line is a program name followed by arguments; the shell replaces variables such as ${analysis_dir} by folder paths before the program starts.
  • PLINK: one command, one pass, a fixed order. Flags choose the operations, PLINK applies them in its own fixed order whatever order you type them in, and --out names every file it writes.
  • R: read, reshape, plot. fread() reads PLINK's space-padded tables, dplyr filters rows and adds columns, and ggplot2 maps columns to the axes of a plot.
  • GrafAnc: distances to reference populations. For each person on their own, it compares the genotypes at up to 282,424 selected SNPs with the allele frequencies of reference populations and reports scores and a group code.
  • Supporting tools install and fetch. git copies repositories, conda, Homebrew and Docker install programs, htslib lets GrafAnc read VCF input, and bcftools works on VCF files.
  • One lookup table maps each QC task to its tool, its command or function, and its output file.

The shell: how a typed line becomes a program run Core

A terminal is a window where you type commands and read their text output: Terminal on macOS, Windows Terminal for Linux under Windows, or the Terminal tab of RStudio. The program inside the terminal that reads each line is the shell. The practical's code chunks run in bash, the standard shell on Linux; macOS terminals start zsh by default, which treats every command on this page the same way.

Before anything runs, the shell rewrites the line in four steps:

  1. It joins a line that ends in a backslash \ with the next line, so one long command can be typed over several lines.
  2. It replaces each variable reference such as ${analysis_dir} with the variable's value.
  3. It splits the result into words at spaces.
  4. It treats the first word as the program's name and looks for a file of that name in each folder listed in the PATH variable, in order. The remaining words become the program's arguments.

Take the practical's first command and suppose the three folder variables hold the paths that Set up your computer creates:

bash 
$ input_dir=$HOME/statgen-workshop/data/inputs/penncath_withPheno
$ analysis_dir=$HOME/statgen-workshop/analysis
$ plink --bfile ${input_dir}/penncath --missing --out ${analysis_dir}/penncath

For a user whose home folder is /home/ana, PLINK receives exactly these words. Programs number them from 0, so this table is the argument vector that PLINK's code reads:

The argument vector PLINK receives for the first command (home folder /home/ana)
IndexWord

2/home/ana/statgen-workshop/data/inputs/penncath_withPheno/penncath
3--missing

5/home/ana/statgen-workshop/analysis/penncath

PLINK never sees ${input_dir}; it sees a path. If the variable is not set, the shell substitutes an empty string, PLINK receives /penncath, and it stops with an error that it cannot open /penncath.bed. That is the most common failure when people copy the practical's commands into a new terminal.

Variables, the environment and the working directory

An environment variable is a named value that a process passes on to every program it starts. In bash, export analysis_dir=… sets one for the current shell and its children, and ${analysis_dir} reads it; in R, Sys.setenv() sets one and Sys.getenv() reads it. PATH and HOME are environment variables that every system sets. The practical defines input_dir, reference_dir and analysis_dir in R and then calls Sys.setenv(), because each bash chunk of an R Markdown document is run as a new bash process started by R: it inherits R's environment but nothing that an earlier bash chunk set.18 In a terminal you set the variables once per session, or put the export lines in your shell's start-up file (Set up your computer writes them for you).

The working directory is the folder a process is running in. A relative path such as analysis/penncath.imiss is looked up from it; cd changes it in the shell, setwd() in R. The practical writes every path in full from the three variables, so its commands work from any folder. The one exception is cd ${analysis_dir} before git clone, which makes the copied repository land in the analysis folder.

Exit status: how a script knows a command failed

Every program ends by returning a whole number to the shell: 0 for success, anything else for failure. a && b runs b only if a succeeded; a || b runs b only if a failed. The practical writes its first merge as plink … --bmerge … || true: that merge is expected to fail (step 7), and true is a program that does nothing and succeeds, so the line as a whole succeeds and knitting continues to the next chunk.

gsub("\"", "", $1) deletes the quote characters from field 1, the family ID. print then writes four fields separated by spaces: the old family ID with its quotes put back (so that it matches the .fam file exactly), the old individual ID, the same family ID as the new family ID, and a new individual ID that joins the two, "10002_1". These are the four columns that --update-ids expects. Pitfall Invisible characters break commands

A backslash continues a line only if it is the very last character: a space after it ends the command there, and the next line runs as a separate, broken command. A path that contains a space is split into two arguments unless it is quoted ("${analysis_dir}"); the practical's paths have no spaces, and the folder layout on Set up your computer keeps it that way. A script saved with Windows line endings (carriage return plus line feed) makes bash report $'\r': command not found; save scripts with Unix line endings.

PLINK 1.9: how it works and how to read a command Core

PLINK is a free, open-source command-line program for genotype data. It reads and writes genotype files, filters people and variants, computes the statistics that quality control needs (missing-call rates, allele frequencies, Hardy–Weinberg tests, linkage disequilibrium, relatedness, principal components) and runs association tests. Every QC statistic in the practical comes from PLINK 1.9.

Where PLINK comes from

Shaun Purcell and colleagues released PLINK in 2007 as a "tool set for whole-genome association and population-based linkage analyses"; version 1.07 was the last of that line.3 Christopher Chang then rewrote its internals as PLINK 1.9, published in 2015 as "second-generation PLINK". It keeps the command-line interface and the file formats of 1.07, and replaces the algorithms with ones that work on many genotypes per processor instruction; for several commands the authors report speedups that "frequently exceed two, and sometimes even three, orders of magnitude".2 After years of numbered beta versions, PLINK 1.9.0 was released as stable on 27 September 2026.4 The practical's input files were written in 2023 by version 1.90b7, as their .log file shows below. PLINK 2.0 is a separate, newer program with its own file format (see below).

Why it is fast: two bits per genotype

A genotype call at a diallelic SNP has four possible values: two homozygous genotypes, the heterozygous genotype, and "missing". Four values fit in two bits, so the .bed file stores four calls per byte, with all the people's calls for one variant stored next to each other (the byte-level layout is on The data: PLINK files inside out). That fixes the size of the file:

\[ \text{bytes} = 3 + m \left\lceil \frac{n}{4} \right\rceil \]
\(3\)
The header: two "magic number" bytes that identify a PLINK .bed file and one byte saying that variants are stored one after another.
\(m\)
The number of variants, one per line of the .bim file.
\(n\)
The number of people, one per line of the .fam file.
\(\lceil n/4 \rceil\)
Bytes per variant: \(n/4\) rounded up to a whole number, because each variant starts on a new byte and unused bit pairs at the end are padding.

Four people share a byte, so the file grows by one byte per variant for every four people. PennCATH has \(n = 1401\) people, so each variant takes \(\lceil 1401/4 \rceil = 351\) bytes; with \(m = 861{,}473\) variants the file has \(3 + 861{,}473 \times 351 = 302{,}377{,}026\) bytes, exactly the size of penncath.bed. The 1000 Genomes reference fileset has 2,504 people and 17,490 SNPs: \(3 + 17{,}490 \times 626 = 10{,}948{,}743\) bytes, again exactly its size. A file of any other size is truncated or corrupt, which makes this a quick check of a download.

PLINK keeps the genotypes in memory in the same two-bit form and processes them 64 bits, that is 32 calls, at a time. Counting the missing calls of a variant shows how. In the .bed code a missing call is the bit pair 01: low bit 1, high bit 0. For a 64-bit word w, the expression w & ~(w >> 1) & 0x5555555555555555 leaves a 1 exactly in the low bit of every pair that reads 01, and a single population-count (popcount) instruction counts those 1 bits. PLINK 1.9's function count_01() does precisely this, so one pass of three bitwise operations and a popcount handles 32 people.14 Distances between people for --genome and the r² values for --indep-pairwise are computed with similar bit tricks.2

Anatomy of a command

A PLINK command is the program name followed by flags. A flag starts with two dashes and may be followed by parameters, separated by spaces. Here is the practical's sample-missingness filter, broken into its parts:

plink --bfile ${analysis_dir}/penncath.geno0.01 --mind 0.01 --make-bed --out ${analysis_dir}/penncath.geno0.01.mind0.01
  1. plink — the program. The shell finds it in a folder on PATH.
  2. --bfile PREFIX — the input: PLINK reads PREFIX.bed, PREFIX.bim and PREFIX.fam. Give the prefix without an extension.
  3. --mind 0.01 — a filter with one parameter: remove every person whose missing-call rate is greater than 0.01. Without the number the threshold is 0.1.
  4. --make-bed — an output command: write the people and variants that are left as a new fileset.
  5. --out PREFIX — the prefix of every file this run writes: PREFIX.bed, .bim, .fam, .log and, if anyone is removed, .irem. Without --out the prefix is plink.

Five rules cover every command in the practical:

  • The order of flags on the line does not matter. PLINK reads all of them first and then works in its own fixed order (next section).
  • One run reads one fileset (plus, with --bmerge, a second one to merge in) and writes files with one prefix. The practical's file names record the steps applied so far (penncath.geno0.01.mind0.01), so the name of a file tells you what was done to it.
  • Filters do nothing lasting on their own. --geno, --mind, --maf, --hwe, --extract and --remove change the data only inside the current run; a report or --make-bed in the same command must use the result. A run with filters and nothing else prints "Warning: No output requested" and stops.
  • Reports change nothing. --missing, --hardy, --het, --genome, --pca and --indep-pairwise write tables or lists; the fileset stays as it was.
  • Every run writes a log. PREFIX.log holds the command, the counts PLINK printed and any warnings.

Two more flags matter on a laptop or a small cloud machine. By default PLINK reserves half of the computer's memory for its workspace and runs multithreaded steps on every processor core; --memory 4000 caps the workspace at 4,000 MB and --threads 2 limits it to two cores.12

Five consequences explain choices in the practical:

  • --mind runs before --geno. In one command, each person's missing rate would be computed over all variants, including the badly genotyped ones that --geno is about to remove, so more people would fail. The practical therefore removes bad variants in one command and bad samples in the next.
  • The --missing report reflects the data after --mind and before --geno when they share a command; the practical runs --missing on its own, so its reports describe the input as it is.
  • --extract acts early, so everything later in the run (--maf, --pca, --genome, --het) sees only the pruned variants.
  • --maf runs before --pca, so the practical's principal components use only variants with minor allele frequency of at least 0.05.
  • --make-bed comes before the LD-pruning, IBD and heterozygosity reports, and those reports never change the saved fileset: pruning only writes lists, which a later command applies with --extract.

PLINK 2.0: what changed, and why the practical uses 1.9 Optional

PLINK 2.0 (program name plink2) is a redesign by the same developer, still labeled beta (Beta 1.4 of 7 November 2026 at the time of writing).15 Its native format is the .pgen/.pvar/.psam fileset, which can hold imputed dosages and variants with more than two alleles; it still reads and writes PLINK 1 filesets. Many flags keep their names (--extract, --geno, --mind, --maf, --hwe, --indep-pairwise, --pca, --flip, --update-ids, --make-bed), but the reports change:

R: read PLINK's tables, reshape them, plot them Core

R is a programming language and environment for statistics and graphics. In the practical it has one job: read the text tables that PLINK and GrafAnc write, compute a few counts and summaries, and draw histograms and scatter plots. Base R can do all of this, but the practical uses three add-on packages (collections of functions that others have written and published on CRAN, R's package archive): the tidyverse, a set of packages that share one design for tables and plots,19 data.table and glue.

A package is installed once per computer and R version, and loaded in every new R session:

R 
# once: download from CRAN and install (a few minutes; see Set up your computer)
install.packages(c("tidyverse", "data.table", "glue"))

# every session: load into the current R session
library(tidyverse)
library(data.table)
library(glue)

library(tidyverse) loads nine packages at once: ggplot2, dplyr, tidyr, readr, purrr, tibble, stringr, forcats and lubridate. It then prints which of their functions mask (take precedence over) functions of the same name loaded earlier, for example dplyr::filter() over stats::filter(). Loading data.table afterwards prints similar messages, because data.table also defines functions such as first(), last() and between(). These messages are expected; package::function() calls a specific package's version when it matters. The practical repeats the three library() lines at the start of later sections so that each section also works when run on its own.

data.table and fread: read any PLINK report in one call

Every R step of the practical starts with fread() from data.table. It reads a delimited text file into a table and decides the format by sampling lines of the file: which character separates the columns, whether the first line is a header, and the type of each column (integer, number or text). PLINK 1.9 pads its reports with runs of spaces so that the columns line up; when the separator is a space, fread() treats a run of spaces as one separator and ignores spaces at the start and end of a line, so these files read without options.20 The result is a data.table, which is also an ordinary R data frame, so the tidyverse functions below work on it.

Two details of these files trip up new R users:

  • No header in .eigenvec. PLINK writes this file without a header line unless asked to with --pca header.13 fread() then names the columns V1, V2, … in order: family ID, individual ID, then the 20 principal components. That is why the practical writes rename(PC1 = V3, PC2 = V4).
  • Column names with parentheses. O(HOM) and N(NM) are not valid R names, because R would read O(HOM) as a call of a function O. Enclose such names in backticks: `N(NM)` - `O(HOM)`.

data.table also has its own compact syntax, DT[i, j, by]: i selects rows, j computes something from the columns, and by groups. .N means "number of rows".

R 
variant_miss <- fread(file.path(analysis_dir, "penncath.lmiss"))
variant_miss[F_MISS > 0.01, .N]                 # number of variants with more than 1% missing calls
variant_miss[, .N, by = .(above = F_MISS > 0.01)]  # both counts, as a two-row table

The second line gives the same two counts as the practical's mutate() + group_by() + tally() pipeline in the next section; which style to use is a matter of taste. data.table is also fast on large tables: it reads with several processor threads and modifies tables in place instead of copying them.

dplyr and the pipe: one verb per step

dplyr, the tidyverse's package for manipulating tables, gives each common operation its own function, named by a verb. Each takes a table as its first argument and returns a new table:

filter(TEST == "UNAFF")
Keep the rows for which the condition is true (here the Hardy–Weinberg rows for PLINK's controls, the people coded 1).
mutate(het_rate = …)
Add a column computed from other columns, or replace one.
group_by(x) + tally() or summarise()
Split the rows into groups by the values of x and count or summarize each group.
count(x, sort = TRUE)
Shortcut for group_by(x) + tally(), largest group first.

The pipe operator %>% chains these steps: x %>% f(y) means f(x, y), so a pipeline reads from top to bottom in the order the steps happen. R 4.1 added a built-in pipe, |>, which works the same way in code like the practical's. This pipeline counts the variants above the practical's 1% threshold:

ggplot2: a plot is data, aesthetics and layers

ggplot2 builds a plot from parts joined with +, following Wickham's "layered grammar of graphics":21

  • ggplot(data, aes(x = F_MISS)) names the table and the aesthetic mappings: which column goes on the x axis, the y axis, or sets color.
  • geom_histogram(), geom_point() add layers, the marks drawn. A histogram cuts the x axis into 30 bins by default and prints a message saying so; give bins = or binwidth = to choose.
  • labs(title = …), xlim(0, 1), theme_classic() set titles, axis ranges and the overall look.

Layers are drawn in order, and each can use its own data. The practical's reference-PCA plot uses this: a first geom_point() layer draws the 1000 Genomes samples colored by super_pop, and a second layer draws the PennCATH samples (whose super_pop is NA after the join) in black on top. In R Markdown a plot appears in the knitted document; in a script, ggsave("plots/pc1_pc2.png", width = 6, height = 4) writes the last plot to a file.

glue: put values into text

glue builds a string from text and R expressions in braces: glue("{n} variants have F_MISS above 0.01") replaces {n} with the value of n. The practical loads glue, but none of its R code calls it. It is handy for building file names from a threshold, for example file.path(analysis_dir, glue("penncath.geno{geno}.lmiss")) with geno <- 0.01.22

Principal components from scikit-learn versus PLINK. Write \(X\) for the \(n \times m\) matrix of standardized genotypes, one row per person and one column per SNP: each count of the counted allele minus its column mean \(2\hat{p}_j\), divided by \(\sqrt{2\hat{p}_j(1 - \hat{p}_j)}\). PLINK 1.9's --pca computes the genetic relationship matrix \(XX^{\mathsf{T}}/m\), finds its top eigenvectors, and writes them to .eigenvec with each column scaled to length 1, with the matching eigenvalues in .eigenval.11,14 scikit-learn's PCA().fit_transform(X) returns the projections of the people onto the same directions. The two are related by:

\[ t_{ik} \approx \pm\, u_{ik} \sqrt{m\, \lambda_k} \]
\(i\)
A person, \(1, \ldots, n\).
\(k\)
A principal component, \(1, \ldots, 20\) for PLINK's default.
\(t_{ik}\)
scikit-learn's score of person \(i\) on component \(k\): column \(k\) of fit_transform(X).
\(u_{ik}\)
PLINK's value for person \(i\) in column \(k + 2\) of the .eigenvec file. Over all \(n\) people, the squares of a column add up to 1.
\(m\)
Number of SNPs used, after --extract, --maf and any other filters in the command.
\(\lambda_k\)
Line \(k\) of the .eigenval file: the \(k\)-th largest eigenvalue of the relationship matrix.
\(\pm\)
The sign of each eigenvector is arbitrary, so a component may come out mirrored.

Both programs decompose the same matrix \(X\). Its singular value decomposition \(X = USV^{\mathsf{T}}\) gives scikit-learn's scores as \(US\) and the relationship matrix as \(XX^{\mathsf{T}}/m = U (S^2/m) U^{\mathsf{T}}\), so PLINK's eigenvectors are the columns of \(U\) and its eigenvalues are \(s_k^2/m\); solving for the singular value gives \(s_k = \sqrt{m\lambda_k}\). Because each PLINK column has length 1, its values shrink as the sample grows: their root mean square is \(1/\sqrt{n}\), which for 1,380 people is \(1/\sqrt{1380} \approx 0.027\). As an illustration with made-up numbers, \(m = 100{,}000\) SNPs and \(\lambda_1 = 10\) give \(\sqrt{m\lambda_1} = 1000\), so a PLINK value of 0.03 corresponds to a scikit-learn score of about 30. The relation is approximate because PLINK computes the diagonal of the relationship matrix with a slightly different estimator, and because a Python analysis must first fill in missing genotypes (for example with the column mean).

A quick check that you are reading PLINK's file correctly: the squares of each PC column add up to 1, which colSums(as.matrix(pcs[, 3:22])^2) in R or (pcs.iloc[:, 2:22] ** 2).sum() in Python shows.

Pitfall pandas-plink counts the other allele

pandas-plink's read_plink(prefix) returns the .bim table, the .fam table and the genotypes as a variants × people array. It calls the two allele columns of the .bim file a0 and a1, so its a0 is PLINK's allele 1 and its a1 is PLINK's allele 2, and a genotype value of 2 means two copies of a1.31 Its numbers therefore count PLINK's allele 2, usually the major allele, while PLINK's own allele counts (for example --recode A) count allele 1. Compare one SNP's genotype counts with the GENO column of the .hwe file before combining the two.

GrafAnc: ancestry groups from distances to reference populations Core

GrafAnc is a command-line program by Yumi Jin and colleagues at the University of Pennsylvania that assigns each person to a genetic ancestry group and estimates three ancestry proportions.23,24 It succeeds GRAF-pop, which the same first author developed at NCBI.25 The version in the practical is 1.0.0 of 18 May 2025, released under the MIT license. Unlike the PCA of steps 6 and 7, it needs no merge with a reference panel: the reference information ships with the program as a table of allele frequencies.

What goes in

  • A genotype file: a PLINK binary fileset (given as its prefix) or a VCF file. Variants are matched by rsID or by chromosome position in genome build GRCh37 or GRCh38; GrafAnc works out which on its own. PennCATH's variant IDs are rsIDs.
  • 282,424 ancestry SNPs, chosen by the authors and already thinned for linkage disequilibrium, so no LD pruning is needed. Missing SNPs lower the accuracy without biasing the estimates; the documentation asks for at least 10,000 genotyped ancestry SNPs per person for continental groups and 50,000 for subcontinental ones, and GrafAnc gives no result below 100.23
  • One person at a time. Each person's result depends only on that person's genotypes, so relatives and duplicates do no harm, files can be split and the results combined, and missing calls need not be filtered first.
  • Unique sample names. GrafAnc names each person by the individual ID, column 2 of the .fam file, and warns about duplicates. Every PennCATH individual ID is 1, which is why step 8 first runs --update-ids (the awk program in the shell section).

The reference table, cpp/data/AncSnpPopAFs.txt, has one line per ancestry SNP: chromosome, position in GRCh37 and GRCh38, rs number, the two alleles, and the allele frequency in each of 26 reference populations. The first three, labeled UKBBEUR, UKBBAFR and UKBBEAS, are the European (E), African (F) and East Asian (A) references of the continental scores; the others (from Nigeria, Ghana, … Finland, Italy, France, Poland, and groups of UK Biobank participants) serve the subcontinental scores. The repository stores the table compressed (28 MB); GrafAnc reads the decompressed text (75.5 MB), which is why the practical runs gunzip once.

How it computes

Step 1: a distance to each reference population. For each person and each reference population, GrafAnc asks how probable the person's genotypes are under that population's allele frequencies, assuming Hardy–Weinberg proportions, and averages the negative log-probability over SNPs:

\[ D_{ik} = -\frac{1}{m_i} \sum_{j=1}^{m_i} \ln \Pr(g_{ij} \mid p_{jk}) \]
\(i\)
A person in the input file.
\(k\)
A reference population; for the continental scores, E, F or A.
\(m_i\)
Number of ancestry SNPs at which person \(i\) has a genotype call (SNPs at which population \(k\)'s frequency is exactly 0 or 1 are skipped).
\(g_{ij}\)
Number of copies, 0, 1 or 2, that person \(i\) carries at SNP \(j\) of the allele whose frequency the table lists.
\(p_{jk}\)
Frequency of that allele in population \(k\).
\(\Pr(g \mid p)\)
Hardy–Weinberg genotype probability: \(p^2\) for \(g = 2\), \(2p(1 - p)\) for \(g = 1\), \((1 - p)^2\) for \(g = 0\).
\(D_{ik}\)
Genetic distance of person \(i\) from population \(k\); 0 would mean every genotype had probability 1.

A genotype that is common in population \(k\) has a probability near 1 and adds little to the sum; a genotype that is rare there adds a lot. At a SNP where the allele has frequency 0.9 in E and 0.1 in F, a person with two copies adds \(-\ln 0.81 = 0.21\) to the sum for E and \(-\ln 0.01 = 4.61\) to the sum for F. Dividing by \(m_i\) makes distances comparable between people genotyped at different numbers of SNPs. This is the distance of GRAF-pop, the program's predecessor.25

Step 2: a position in the E–F–A triangle. GrafAnc also computes the distances expected for a typical member of E, of F and of A over the same SNPs. These three expected points form a triangle, and the person's three distances form a fourth point. After rotating the points so that the triangle lies flat, GrafAnc expresses the person's position by barycentric coordinates \(\lambda_{\mathrm{E}}, \lambda_{\mathrm{F}}, \lambda_{\mathrm{A}}\): three weights that add up to 1 and give the point as a weighted average of the triangle's corners. GD1 and GD2 are those weights applied to a fixed triangle, so every dataset is drawn on the same axes; GD3 is the person's distance from the plane of the triangle.23

\[ \begin{aligned} \mathrm{GD} &= \lambda_{\mathrm{E}} \mathbf{v}_{\mathrm{E}} + \lambda_{\mathrm{F}} \mathbf{v}_{\mathrm{F}} + \lambda_{\mathrm{A}} \mathbf{v}_{\mathrm{A}} \\ P_{\mathrm{e}} &= \frac{100 \max(0, \lambda_{\mathrm{E}})}{\sum_{k} \max(0, \lambda_k)} \end{aligned} \]
\(\mathrm{GD}\)
The person's point (GD1, GD2).
\(\mathbf{v}_{\mathrm{E}}, \mathbf{v}_{\mathrm{F}}, \mathbf{v}_{\mathrm{A}}\)
The fixed corners: E = (1.4758, 1.4370), F = (1.0800, 1.1000), A = (1.7045, 1.1000) in (GD1, GD2) coordinates.
\(\lambda_{\mathrm{E}}, \lambda_{\mathrm{F}}, \lambda_{\mathrm{A}}\)
Barycentric coordinates, with \(\lambda_{\mathrm{E}} + \lambda_{\mathrm{F}} + \lambda_{\mathrm{A}} = 1\). GrafAnc reports \(100\lambda\) as RawPe, RawPf, RawPa.
\(k\)
Runs over E, F and A in the sum.
\(P_{\mathrm{e}}\)
The reported Pe, in percent; Pf and Pa are defined the same way.

Inside the triangle all three weights lie between 0 and 1, and they are the reported percentages directly. At a corner one weight is 1; on an edge the weight of the opposite corner is 0. Outside the triangle one weight turns negative; Pe, Pf, Pa set it to 0 and rescale the other two to add to 100, while the raw columns keep it. Because F and A share \(\mathrm{GD2} = 1.1\), the European weight depends on GD2 alone: \(\lambda_{\mathrm{E}} = (\mathrm{GD2} - 1.1)/0.337\). For a person at (1.2779, 1.2685) this gives \(\lambda_{\mathrm{E}} = 0.1685/0.337 = 0.5\), and then \(\lambda_{\mathrm{F}} = 0.5\), \(\lambda_{\mathrm{A}} = 0\) reproduce \(\mathrm{GD1} = 0.5 \times 1.4758 + 0.5 \times 1.08 = 1.2779\): Pe = 50, Pf = 50, Pa = 0, the midpoint of the E–F edge.

Step 3: subcontinental scores. Each of the fifteen columns EA1–EA4, AF1–AF3, EU1–EU3, SA1, SA2 and IC1–IC3 compares two of the reference populations. For each SNP it takes the logarithm of the ratio of the person's genotype probabilities under the two populations' frequencies, averages over SNPs, and rescales the average so that a typical member of the first population scores −1 and a typical member of the second scores +1.23

Step 4: a group by fixed rules. AncGroupID comes from a sequence of hand-set thresholds on these scores, checked in order. In the source code, for example, a person with Pa above 15 and Pf above 15 who has not matched the earlier Oceania and South Asia rules is assigned 800 (multi-ancestry); a person with EU1 below 1.6 and IC2 below −0.25 enters the Europe and Middle East branch, where IC3 below 3.5 − 3.1 × EU1 means Europe, and EU2, EU3 then pick the European subgroup.23 The first digit of the code is the continental group, which is what the practical's AncGroupID %/% 100 extracts (integer division by 100).

How precise is a score? The documentation estimated the standard deviation of each score by deleting genotypes at random in 1000 Genomes data:23

\[ \sigma \approx a + \frac{b}{\sqrt{n}} \]
\(\sigma\)
Standard deviation of a score caused by which SNPs happen to be genotyped.
\(n\)
Number of ancestry SNPs with a genotype call: the SNPs column.
\(a, b\)
Constants fitted for each score and listed in the documentation; for GD2, \(a = -0.0001\) and \(b = 0.95\).

Each score is an average over SNPs, and the standard deviation of an average falls as one over the square root of the number of terms; \(a\) is a small correction from the fit. For GD2 at \(n = 10{,}000\), \(\sigma = -0.0001 + 0.95/100 = 0.0094\). Since \(\lambda_{\mathrm{E}} = (\mathrm{GD2} - 1.1)/0.337\), that is \(0.0094/0.337 \approx 0.028\) in \(\lambda_{\mathrm{E}}\), or about 2.8 percentage points of Pe. With all 282,424 SNPs it falls to about 0.5 points.

Running it: the binary, GRAFPATH, bcftools and the workshop patch

  • Linux only. The repository includes a ready-built program, bin/grafanc, for 64-bit Linux, and the practical runs that file. The source code uses Linux-specific system interfaces (it reads the machine's memory size with sysinfo() and finds its own location through /proc/self/exe), so it does not compile on macOS or Windows. On those systems run it in Docker or in WSL (Set up your computer).
  • GRAFPATH. GrafAnc looks for AncSnpPopAFs.txt in the current folder, next to the executable, in ../cpp/data relative to it, and finally under the folder named by the environment variable GRAFPATH. The practical sets GRAFPATH=${analysis_dir}/grafanc/cpp so the search ends in cpp/data.
  • Why module load bcftools/1.23? GrafAnc never runs bcftools. Its makefile links it against htslib, the C library for reading VCF and other sequencing formats on which bcftools is built, and its README says htslib must be installed. Loading the bcftools module on Biowulf most likely makes that library available to the ready-built program. This is our inference from the files; the practical does not give the reason.
  • The workshop patch. The workshop's Docker image (ghcr.io/dceg-workshops/graftools) builds GrafAnc from source with a small patch.26 The patch rewrites the output step, which in the original builds each line with sprintf() writing into the same buffer it reads from (behavior the C standard leaves undefined) and can stop early when some people have too few SNPs; it frees arrays with delete[]; and it makes the program exit with status 0 after a successful run. The original returns 1 on success and 0 on most errors, the reverse of the convention in Exit status. In the practical this does no harm, because the chunk's last command, head, succeeds; in a script that stops at the first failure it matters (the downloadable pipeline allows for it).

Key points
  • The shell turns a typed line into a program name and a list of arguments; PLINK sees paths, never ${variables}, and a non-zero exit status means failure.
  • PLINK 1.9 stores four genotypes per byte, so a .bed file has exactly \(3 + m\lceil n/4 \rceil\) bytes, and it processes 32 genotypes per 64-bit operation.
  • One PLINK run reads one fileset, applies its flags in a fixed documented order (--mind before --geno, merge first, --make-bed before the reports), and writes files that all share the --out prefix, including a .log.
  • R reads every report with fread(); .eigenvec has no header (columns V1, V2, …), and names like O(HOM) need backticks.
  • GrafAnc places each person in a fixed E–F–A triangle from Hardy–Weinberg distances to reference allele frequencies, turns the position into Pe, Pf, Pa, and assigns AncGroupID by fixed rules. It runs on Linux only.

Check your understanding

Someone shortens step 1 to plink --bfile penncath --geno 0.01 --mind 0.01 --make-bed --out clean. Which filter acts first, and why might more people be removed than in the practical?

--mind acts first: PLINK applies sample filters before variant filters whatever the order on the command line. Each person's missing rate is then computed over all variants, including the badly genotyped ones that --geno would have removed, so rates are higher and more people exceed 0.01. The practical runs --geno and --mind as two separate commands for this reason.

A fileset has 3,884 people and 17,490 SNPs. How many bytes must its .bed file have?

Each SNP takes \(\lceil 3884/4 \rceil = 971\) bytes, so the file has \(3 + 17{,}490 \times 971 = 16{,}982{,}793\) bytes. Any other size means a truncated or corrupt file.

Why does the practical keep only the rows with TEST == "UNAFF" from the .hwe file?

For case/control data PLINK 1.9's --hardy writes three rows per variant: all founders (ALL), cases (AFF) and controls (UNAFF). A SNP associated with the disease can legitimately depart from Hardy–Weinberg proportions in cases, so the QC check uses controls; PLINK's --hwe filter also tests controls only.

Why does mutate(het_rate = (N(NM) - O(HOM)) / N(NM)) fail, and what fixes it?

R reads N(NM) as a call of a function named N with argument NM. Column names that are not valid R names must be enclosed in backticks: (`N(NM)` - `O(HOM)`) / `N(NM)`.

The first --bmerge fails. Which new files are in analysis_dir, and why does the practical end the command with || true?

PLINK writes penncath.geno0.01.mind0.01.merge1kgenomes-merge.missnp, the list of variants with apparent three-allele conflicts, and the run's .log, but no merged fileset. It exits with a non-zero status, which would stop the knitting; || true replaces that status with success so the next chunk, which flips the listed SNPs, can run.

GrafAnc reports GD1 = 1.4201 and GD2 = 1.2123 for a person. What are Pe, Pf and Pa?

\(\lambda_{\mathrm{E}} = (1.2123 - 1.1)/0.337 = 0.333\). Then \(\lambda_{\mathrm{A}} = (1.4201 - 0.333 \times 1.4758 - 0.667 \times 1.08)/0.6245 = 0.333\), where 0.6245 is the distance from F to A along GD1, and \(\lambda_{\mathrm{F}} = 1 - 0.333 - 0.333 = 0.333\). All three are about 33: the point is the centroid of the triangle.

The practical loads the bcftools module before running GrafAnc, yet never calls bcftools. What is the most likely reason?

GrafAnc is linked against htslib, the library bcftools is built on, and its README says htslib must be installed. On Biowulf, loading the bcftools module most likely makes that shared library available to the ready-built GrafAnc program. The practical does not state the reason; this is an inference.

A PLINK .eigenvec value is 0.03 while scikit-learn gives about 30 for the same person and component. Is one of them wrong?

Not necessarily. PLINK writes eigenvectors scaled to length 1; scikit-learn writes projections, which are larger by \(\sqrt{m\lambda_k}\) (up to sign). With \(m\lambda_k = 10^6\) the factor is 1000. Check that the squares of each PLINK column add up to 1.
