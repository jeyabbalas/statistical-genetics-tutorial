The data: PLINK .bed, .bim and .fam files, inside out

The practical's genotypes come as three files named penncath: a text file that lists the 1,401 people, a text file that lists the 861,473 SNPs (single-nucleotide polymorphisms: positions in the genome where people differ by one DNA letter), and a binary file that holds every genotype call, the pair of alleles the genotyping software assigned to one person at one SNP, in two bits. This page opens each file, decodes real genotypes from the raw bytes by hand, and shows how R and Python read the same files, including the readers that count the other allele without saying so.

≈ 45 min Shows up in the data as: penncath.bed · penncath.bim · penncath.fam
Mental model

A fileset is one genotype matrix kept in three files

A PLINK binary fileset is one matrix of genotype calls, people by SNPs, kept in three files that share a name. The .fam file names the rows, the .bim file names the columns and says which allele the numbers count, and the .bed file holds the entries at two bits each, one SNP after another. Nothing but the order of the lines ties the three together.

  • Rows: the .fam file. One line per person, in the order of the genotypes, with six columns: family ID, individual ID, father, mother, sex and phenotype.
  • Columns: the .bim file. One line per SNP, in the order of the genotype blocks: chromosome, SNP ID, two positions, and the alleles A1 and A2. A stored genotype is the number of copies of A1.
  • Entries: the .bed file. Three header bytes, then one block of \(\lceil n/4 \rceil\) bytes per SNP for \(n\) people; each byte holds four people's 2-bit codes, the first person in the lowest bits.
  • By hand. A hex dump of penncath.bed and a little arithmetic recover real genotypes, which is also how you test any reader.
  • In memory. The matrix has 1.2 billion entries: 0.3 GB packed, 9.7 GB as 64-bit numbers. R and Python readers differ in layout, size and in which allele they count.

The .fam file: one line per person Core

The genotypes were measured for the PennCATH study and later released for teaching with a tutorial paper by Reed and colleagues.6 The .fam file is plain text with no header line. Each line describes one person, and the line number is the person's position inside every SNP's block of the .bed file: line 1 is the first genotype of each block, line 2 the second, and so on. Nothing else connects a person to their genotypes. These are the first four lines and the last line of penncath.fam:

bash 
$ head -n 4 penncath.fam
$ tail -n 1 penncath.fam
Output 
"10002" 1 0 0 1 1
"10004" 1 0 0 2 1
"10005" 1 0 0 1 2
"10007" 1 0 0 1 1
"11596" 1 0 0 1 -9

The six columns are separated by spaces (tabs are also allowed). PLINK's documentation defines them as follows; the notes say what this file holds.2

1 · FID
Family ID, a label shared by the members of one family. The PennCATH participants are unrelated, so each person's FID is their study number. The quotation marks are part of the ID: PLINK reads the first person's FID as the seven characters "10002", quotes included.
2 · IID
Individual ID within the family; it cannot be 0. Every IID in this file is 1. That is allowed, because PLINK identifies a person by the pair (FID, IID), but programs that read the IID alone, such as GrafAnc in step 8 of the practical, would see 1,401 people with the same ID, so step 8 builds unique IIDs first.
3 · father
The father's IID, or 0 if the father is not in the file. All 0 here.
4 · mother
The mother's IID, or 0. All 0 here. A person whose father and mother IDs are both 0 is a founder; a parent ID that is filled in makes the person a nonfounder even if that parent is not in the file. PLINK computes allele frequencies, Hardy–Weinberg tests and LD pruning from founders only, which here means everyone.
5 · sex
1 = male, 2 = female, 0 = unknown. 937 people are coded 1 and 464 are coded 2.
6 · phenotype
For a case–control trait, 1 = control, 2 = case, and −9 or 0 = missing. Any other number makes PLINK read the whole column as a quantitative trait, such as a cholesterol level, with −9 still meaning missing. (The option --1 switches to 0 = control, 1 = case.) This file has 470 people coded 1, 463 coded 2 and 468 coded −9; what the codes mean here is the subject of What column 6 holds below.

Counting the values of a column is the quickest check of a .fam file. awk '{print $5}' prints the fifth whitespace-separated field of every line, sort groups equal values, and uniq -c counts each group:

bash 
$ awk '{print $5}' penncath.fam | sort | uniq -c    # sex
$ awk '{print $6}' penncath.fam | sort | uniq -c    # phenotype
Output 
 937 1
 464 2
 468 -9
 470 1
 463 2

The same numbers appear in the PLINK log that came with the files ("1401 people (937 males, 464 females)", "463 are cases and 470 are controls", "468 phenotypes are missing"), which is read line by line on The tools · Read the .log file.

Pitfall Never sort or edit the .fam file on its own

The .bed file contains no IDs to match against, only positions. Sorting the .fam file, deleting a line, or replacing it with the .fam file of another fileset attaches every genotype to the wrong person, and PLINK reports no error as long as the number of lines is unchanged. To change IDs, sex or phenotypes, or to drop people, use PLINK options that rewrite all three files consistently: --update-ids, --update-sex, --pheno, --keep and --remove, followed by --make-bed.3

What column 6 holds in this copy of PennCATH

The practical describes column 6 as coronary artery disease (CAD) case–control status: 1 = control, 2 = case, −9 = missing.8 A second source gives a different picture. The teaching copy of PennCATH distributed by Patrick Breheny comes with a clinical table, penncath.csv, that records CAD for all 1,401 people ("CAD=1 means that the subject has coronary artery disease").7 Matching that table to penncath.fam on the family ID gives:

Code in column 6PeopleCAD in the clinical table
1470CAD = 1 for all 470
2463CAD = 1 for all 463
−9468CAD = 0 for all 468

By the clinical table, then, the 468 people with a missing phenotype are the people without CAD, and codes 1 and 2 divide the 933 people with CAD into two groups. We found no documentation of what that division is. (In Breheny's copy the 468 are coded 0, which PLINK reads as missing and wrote as −9 when the files were rewritten for the workshop.) For quality control the consequence is small: only step 2 uses the phenotype, and there the "controls" (PLINK's UNAFF group) are the 470 people coded 1. The general lesson matters more: PLINK cannot know what a phenotype column means, so check it against the study's own documentation before any association analysis.

The .bim file: one line per SNP Core

The .bim file (PLINK calls it the "extended MAP file") is also plain text with no header. Each line describes one SNP, in the order of the SNP blocks of the .bed file. Its columns are separated by tabs. These are its first eight lines and its last line:

$ tail -n 1 penncath.bim

1 · chromosome
1–22 for the autosomes; PLINK codes X, Y, the pseudo-autosomal region of X and Y, and mitochondrial DNA as 23, 24, 25 and 26 in its output; 0 means unknown. This file has autosomes only, from 71,038 SNPs on chromosome 1 to 11,382 on chromosome 22, and no X chromosome, which is why the practical cannot check recorded sex against the genotypes.
2 · SNP ID
Here the dbSNP rsID, a stable public identifier. Any text without spaces is allowed, and IDs must be unique for most PLINK operations.
3 · genetic position
Position on the genetic map in morgans or centimorgans (a measure of recombination). It is 0 for every SNP here; PLINK's documentation says a dummy 0 is safe.
4 · base-pair position
The 1-based coordinate on the chromosome, which only means something together with a genome build. These positions are on GRCh37: dbSNP places rs12565286 at 721,290 on chromosome 1 in GRCh37, the value on line 2.
5 · A1
Allele 1, defined by the format as the allele of the "clear bits" in the .bed file (code 00) and "usually minor". A stored genotype counts copies of A1.
6 · A2
Allele 2, the allele of the "set bits" (code 11), "usually major".

A1 is the allele that is counted, and PLINK chooses it

When PLINK 1.9 writes a fileset with --make-bed, it makes A1 the minor allele, the less frequent of the two among the people in the file, unless --keep-allele-order is given; the documentation says that "otherwise, the major allele is set to A2".3 In penncath.bim this holds everywhere: decoding the whole .bed file with the code further down, no SNP has an A1 frequency above 0.5. Three consequences follow.

  • A1 is not the reference allele. The reference allele is the letter in the reference genome sequence. At rs12565286 the GRCh37 reference letter is G, and G is also A1, but only because G is the rarer allele in these people (5.2% of called alleles).
  • A1 can change between files. If filtering removes people and a SNP's frequency crosses 0.5, the next --make-bed swaps A1 and A2 for that SNP and every stored count becomes 2 minus its old value. Compare results across files by their A1 column, never by position in a table.
  • A1 is not the risk allele. An association test reports the effect of each extra copy of A1, whichever direction that turns out to be.

A SNP where only one allele was seen in anyone has nothing to put in column 5. PLINK 1.9 writes 0 there; this file has −9 instead, inherited from the file it was made from, and PLINK reads −9 as the name of an allele that no one carries. Either way such a SNP is monomorphic in these people: everyone with a call has the same genotype, so it carries no information for association or QC statistics. Line 1 is one of 26,153 such SNPs. One SNP, rs9428247 on line 35,786, has no calls at all and −9 in both columns.

Counting the unordered allele pairs of the 835,319 SNPs with two known alleles shows which DNA changes the array measures:

DNA has two complementary strands, and a SNP can be reported from either: A pairs with T and C with G, so a C/T SNP read from the other strand is G/A. Line 4 is an example. For most SNPs a mismatch like this can be detected and fixed by complementing the letters, which is what --flip does in step 7 of the practical when the data are merged with the 1000 Genomes reference. For the 128,999 A/T and C/G SNPs it cannot: their complement is the same pair, so the letters alone never reveal the strand. Line 7, rs2980319 (A/T), is one of them.

The .bed file: two bits per genotype Core

The .bed file ("binary biallelic genotype table") is not text, so head is no use; xxd prints a file's bytes in hexadecimal, two digits per byte. (It has nothing to do with the UCSC genome browser's BED format, a text format for genome intervals.) The first 16 bytes:

bash 
$ xxd -l 16 penncath.bed
Output 
00000000: 6c1b 01ff ffff ffff ffff ffff ffff ffff  l...............

The first column is the offset of the first byte shown (0), then come the bytes in file order, grouped two by two, and on the right the bytes as text where they are printable. Everything after the header follows from the format specification:24

  • Bytes 0 and 1, 6c 1b: the "magic number" that marks the file as a PLINK .bed file. Readers check these bytes before anything else; the code further down stops if they are wrong.
  • Byte 2, 01: the layout. 01 means SNP-major: all people's genotypes for the first SNP, then all people's genotypes for the second SNP, and so on. PLINK 1.07 could also write 00, sample-major (all SNPs of the first person, then all SNPs of the second person); PLINK 1.9 converts such a file to SNP-major when it reads one.4
  • From byte 3: one block per SNP, in .bim order. A block holds the genotypes of all \(n\) people in .fam order, four per byte, so it is \(\lceil n/4 \rceil\) bytes long: \(n/4\) rounded up, because every block starts on a fresh byte. For \(n = 1{,}401\) that is 351 bytes.

The first SNP, rs10458597, is monomorphic: everyone with a call has two copies of C, which is A2, so its block is almost entirely ff bytes (four people with code 11 each). Within a block, each person has a 2-bit code:

CodeGenotypeCopies of A1At rs12565286 (A1 = G, A2 = C)
00homozygous for A12G/G
01missing (no call)—no genotype
10heterozygous1G/C
11homozygous for A20C/C

Inside a byte, the first person of the four sits in the two lowest-order bits (the rightmost two when the byte is written in binary), the second person in the next two, and so on, so a byte written in binary reads from right to left. Where a person's genotype lives is therefore a matter of arithmetic:

\[ \begin{gathered} b = 3 + (j - 1)\,B + \left\lfloor \frac{i - 1}{4} \right\rfloor \\ s = 2\,\big((i - 1) \bmod 4\big) \end{gathered} \]
\(i\)
The person's line number in the .fam file, from 1 to \(n\).
\(j\)
The SNP's line number in the .bim file, from 1 to \(m\), the number of SNPs.
\(B = \lceil n/4 \rceil\)
Bytes per SNP block: 351 for the 1,401 PennCATH people.
\(b\)
The offset of the byte that holds the genotype, counting the file's first byte as 0.
\(\lfloor (i-1)/4 \rfloor\)
Which byte of the block: people 1–4 are in byte 0, people 5–8 in byte 1, and so on.
\(s\)
The position of the person's lower bit inside that byte: 0, 2, 4 or 6. The code is the two bits at positions \(s\) and \(s+1\), that is, the byte shifted right by \(s\) bits with all but the last two bits cleared.

The 3 skips the header, \((j-1)B\) skips the blocks of the \(j-1\) SNPs before this one, and the floor term picks the byte of the block; within it, each earlier person of the same byte pushes this one two bits further to the left. For person 2 at SNP 2 (rs12565286): \(b = 3 + 351 + 0 = 354\) and \(s = 2\). The same arithmetic gives the size of the whole file: the last block ends at byte \(3 + mB\), so with \(m = 861{,}473\) SNPs the file has \(3 + 861{,}473 \times 351 = 302{,}377{,}026\) bytes. Because \(1{,}401 = 4 \times 350 + 1\), the last byte of every block holds a single person and six bits of padding, which are always 0.

The file size is the quickest test that the three files belong together: wc -l counts lines and wc -c counts bytes.

bash 
$ wc -l penncath.fam penncath.bim
$ wc -c penncath.bed
Output 
    1401 penncath.fam
  861473 penncath.bim
  862874 total
 302377026 penncath.bed

302,377,026 is exactly \(3 + 861{,}473 \times 351\). PLINK makes the same check when it loads a fileset and stops with an error if the size does not match the line counts, which catches a .fam or .bim file with lines added or lost, but not one whose lines were reordered. Why this layout makes PLINK fast, with the bit operations that count 32 genotypes at a time, is on The tools · Why it is fast.

Pitfall Two documentation pages, two ways of writing the same bits

The PLINK 1.9 page lists the codes with the high bit first, as above: 01 = missing, 10 = heterozygous. The older PLINK 1.07 page writes each code in the order the bits are read, low bit first, and so lists "01 Heterozygote" and "10 Missing genotype".4 Both describe the same file. If a decoder you wrote turns heterozygotes into missing calls and missing calls into heterozygotes, it has mixed the two conventions.

Decode real genotypes by hand Core

The block of the second SNP, rs12565286, starts at byte \(3 + 351 = 354\). Its first eight bytes, in hexadecimal and then the first three in binary (-s sets the start offset, -l the number of bytes, and -b switches to binary):

bash 
$ xxd -s 354 -l 8 penncath.bed
$ xxd -b -s 354 -l 3 penncath.bed
Output 
00000162: f3ff ffdf febf ffeb  ........
00000162: 11110011 11111111 11111111  ...

(162 is 354 in hexadecimal.) Split the first byte, 11110011, into four 2-bit codes and read them from the right:

BitsPerson (.fam line)CodeGenotype
1–01 · "10002"11C/C, 0 copies of G
3–22 · "10004"00G/G, 2 copies of G
5–43 · "10005"11C/C

The next two bytes, ff, are people 5 to 12, all C/C. The remaining five bytes contain the first exceptions: in df = 11011111 the third pair from the right is 01, so person 15 has no call; fe = 11111110 makes person 17 heterozygous (G/C); bf = 10111111 makes person 24 heterozygous; and eb = 11101011 makes persons 30 and 31 heterozygous. The last byte of the block is at offset \(354 + 350 = 704\):

bash 
$ xxd -b -s 704 -l 1 penncath.bed
Output 
000002c0: 00000011  .

Its lowest pair, 11, is person 1,401 ("11596" on the last .fam line): C/C. The other six bits are padding. On a system without xxd, od -A d -t x1 -j 354 -N 8 penncath.bed prints the same bytes with decimal offsets.

The same in a few lines of code

A reader for one SNP needs exactly the arithmetic above: check the header, jump to the block, and pull out each person's two bits. These versions use no packages, and both were run on the real penncath files with the output shown.

python 
# read_bed.py: decode one SNP of a PLINK 1 .bed file with plain Python (no packages).
CODE = {0b00: 2, 0b01: None, 0b10: 1, 0b11: 0}   # 2-bit code -> copies of A1; None = missing

def read_snp(prefix, j, n):
    """Genotypes of SNP j (0-based, in .bim order) for all n people (in .fam order)."""
    bytes_per_snp = (n + 3) // 4                    # ceil(n / 4)
    with open(prefix + ".bed", "rb") as bed:
        assert bed.read(3) == b"\x6c\x1b\x01"       # magic number, SNP-major
        bed.seek(3 + j * bytes_per_snp)             # skip the header and j earlier SNPs
        block = bed.read(bytes_per_snp)
    return [CODE[(block[i // 4] >> (2 * (i % 4))) & 0b11] for i in range(n)]

prefix = "penncath"
n = sum(1 for _ in open(prefix + ".fam"))           # 1401 people
bim = [line.split() for line in open(prefix + ".bim")]
for j in range(4):
    g = read_snp(prefix, j, n)
    called = [x for x in g if x is not None]
    freq = sum(called) / (2 * len(called))
    print(bim[j][1], "A1=" + bim[j][4], "A2=" + bim[j][5],
          "first 12:", g[:12], "missing:", g.count(None), "A1 freq: %.4f" % freq)
Output

r 
# Decode one SNP of a PLINK 1 .bed file in base R (no packages).
read_bed_snp <- function(prefix, j, n) {         # j is 1-based, in .bim order
  bytes_per_snp <- ceiling(n / 4)
  con <- file(paste0(prefix, ".bed"), "rb")
  on.exit(close(con))
  magic <- readBin(con, "raw", 3)
  stopifnot(identical(magic, as.raw(c(0x6c, 0x1b, 0x01))))
  seek(con, 3 + (j - 1) * bytes_per_snp)          # skip the header and earlier SNPs
  block <- as.integer(readBin(con, "raw", bytes_per_snp))
  i <- 0:(n - 1)                                  # person index, 0-based
  code <- bitwAnd(bitwShiftR(block[i %/% 4 + 1], 2 * (i %% 4)), 3L)
  c(2L, NA, 1L, 0L)[code + 1]                     # 00, 01, 10, 11 -> copies of A1
}

Decoding a whole file one SNP at a time this way is slow in pure Python, and vectorized code is the usual next step. The NumPy version below decodes every SNP at once. It is untested: NumPy was not available where this page was written, so check it against the pure-Python reader on a few SNPs before relying on it.

python · not run here 
import numpy as np

def read_bed(prefix, n, m):
    """All genotypes as an n x m int8 matrix of A1 copies, -1 = missing. Untested."""
    bps = (n + 3) // 4                                       # bytes per SNP
    raw = np.fromfile(prefix + ".bed", dtype=np.uint8)
    assert raw[:3].tolist() == [0x6C, 0x1B, 0x01]
    blocks = raw[3:].reshape(m, bps)                         # one row per SNP
    codes = np.stack([(blocks >> s) & 0b11 for s in (0, 2, 4, 6)], axis=2)
    codes = codes.reshape(m, 4 * bps)[:, :n]                 # drop the padding
    lookup = np.array([2, -1, 1, 0], dtype=np.int8)          # codes 00, 01, 10, 11
    return lookup[codes].T                                   # people x SNPs

For PennCATH this holds several copies of the matrix at once, about 2.7 GB at its peak, which is the problem the next section is about.

The genotype matrix in memory Core

PennCATH has \(1{,}401 \times 861{,}473 = 1{,}206{,}923{,}673\) genotypes. How much memory they take depends only on how many bytes each one is given:

RepresentationBytes per genotypePennCATH
2-bit codes: the .bed file, and PLINK 1.9's own memory10.250.30 GB
One byte: NumPy int8, R raw, snpStats11.21 GB
Four bytes: R integer, float3244.83 GB
Text .ped file: two letters and two spaces≈ 4≈ 4.8 GB
Eight bytes: R numeric, NumPy float6489.66 GB

Two bits is the least that can hold four possible values, and it is what makes the .bed format practical: the file is 32 times smaller than a matrix of 64-bit numbers, and reading one SNP means reading one contiguous run of 351 bytes. The practical never loads the matrix into R at all. PLINK reads the .bed file, writes small summary tables (one line per person or per SNP), and R reads only those. Analyses that do need the matrix in R or Python, such as fitting your own models, either read a subset of SNPs or use a reader that keeps the data on disk and fetches what is asked for.

Pitfall The same name for different alleles

"a1" in pandas-plink is PLINK's A2, and "alt" in genio is PLINK's A1, whatever the reference genome says. A reader that counts the other allele returns \(2 - g\) instead of \(g\) for every genotype, so frequencies become one minus themselves and every effect estimate changes sign, without any error. Before trusting a reader, decode one SNP with the ten-line function above and compare: for rs12565286 the mean count should be \(2 \times 0.0517 = 0.103\) copies of G, and a reader that reports 1.897 is counting C.

Other formats that hold the same matrix Optional

The PLINK 1 binary fileset is one of several formats for genotype data; Lecture 0 compares them in Genotype files. What each one does differently:

  • PLINK 2: .pgen, .pvar, .psam. The same three roles, but the genotype file can compress, and can hold phased genotypes, dosages from imputation and SNPs with more than two alleles. The .pvar file names the alleles REF (the reference-genome letter) and ALT instead of A1 and A2, and PLINK 2 does not reorder them by frequency.15
  • VCF (Variant Call Format). A text format from sequencing, one line per variant with REF and ALT and one column per person; it is what reference panels and imputation servers use. See Lecture 0 · VCF files.16
  • BGEN. A compressed binary format for imputed data that stores genotype probabilities rather than calls; UK Biobank distributes its imputed genotypes this way. See Lecture 0 · BGEN files.18
  • .ped and .map. PLINK's original text format, one line per person with two letters per SNP.5 The PLINK 1.9 documentation says it "is NOT a native file format for PLINK 1.9" and "should almost never be used".3

Conversions are one PLINK command each. These were not run here:

bash · not run here 
plink --bfile penncath --recode vcf --out penncath      # penncath.vcf; sample IDs become FID_IID
plink --bfile penncath --recode A --out penncath        # penncath.raw: one column per SNP, 0/1/2 copies of A1
plink2 --bfile penncath --make-pgen --out penncath      # penncath.pgen, .pvar, .psam

Two details matter when converting from a .bed file. PLINK 1.9's VCF output writes A2 as the REF allele and flags it as provisional (a PR entry in the INFO column), because the .bim file does not record which allele the reference genome has. And the .raw file, the usual route into R for a few hundred SNPs, names each column by SNP and counted allele (for example rs12565286_G); for all of PennCATH it would be about 2.4 GB of text.

In the reading Uffelmann et al. 2021 · Experimentation › Data processing

The reading lists what a GWAS starts from: "Input files for a GWAS include anonymized individual ID numbers, coded family relations between individuals, sex, phenotype information, covariates, genotype calls for all called variants and information on the genotyping batch."9 In the practical's files, the IDs, family relations, sex and phenotype are the six columns of penncath.fam, and the genotype calls are penncath.bed with penncath.bim. The covariates (age, cholesterol) would come in a separate table, and the genotyping batch is not part of this copy of the data, which is one reason the practical cannot check for batch effects (see what the practical does not do).

Key points
  • A PLINK binary fileset is one people × SNPs matrix: the .fam file names the rows, the .bim file the columns, and the .bed file holds the entries. Only line order connects them.
  • The .fam file has six columns: FID, IID, father, mother, sex (1/2/0) and phenotype (1 = control, 2 = case, −9 or 0 = missing). In this copy every IID is 1, and column 6 should be checked against the study's documentation.
  • The .bim file has six columns: chromosome, ID, genetic position, base-pair position (GRCh37 here), A1 and A2. Stored genotypes count A1, which PLINK 1.9 sets to the minor allele whenever it writes a fileset.
  • The .bed file is 6c 1b 01 followed by one block of \(\lceil n/4 \rceil\) bytes per SNP; codes 00, 01, 10, 11 mean 2 copies of A1, missing, 1 copy, 0 copies, with the first person in the lowest bits.
  • The file size \(3 + m\lceil n/4 \rceil\) and a hex dump are enough to verify any reader. Readers differ in which allele they count, so check one SNP before trusting one.

Check your understanding

Where in penncath.bed is the genotype of person 3 at the SNP on line 5 of the .bim file, and which bits hold it?

The block of SNP 5 starts at byte \(3 + 4 \times 351 = 1{,}407\). Person 3 is in the first byte of the block, \(\lfloor 2/4 \rfloor = 0\), so the byte is 1,407; the shift is \(2 \times (2 \bmod 4) = 4\), so the genotype is in bits 4 and 5. xxd -b -s 1407 -l 1 penncath.bed shows the byte.

A byte inside a block is 6b, which is 01101011 in binary. What are the genotypes of the four people it holds?

Read the pairs from the right. Bits 1–0 are 11: the first person is homozygous for A2 (0 copies of A1). Bits 3–2 are 10: heterozygous. Bits 5–4 are 10: heterozygous. Bits 7–6 are 01: the fourth person has no call.

Why does every SNP block of penncath.bed end with six bits of padding, and how long would a block be with 1,404 people?

\(1{,}401 = 4 \times 350 + 1\): 350 bytes hold 1,400 people and the 351st byte holds one person in its two lowest bits, leaving three empty pairs, six bits that PLINK sets to 0. With 1,404 people the block is still \(\lceil 1{,}404/4 \rceil = 351\) bytes, with no padding.

Someone sorts penncath.fam by sex and saves it under the same name. What happens the next time PLINK reads the fileset?

Nothing visible: the number of lines is unchanged, so the file size still matches and PLINK runs. But the .bed file still stores genotypes in the original order, so most people now carry someone else's genotypes. Sex and phenotype no longer match the DNA, which would show up only in checks such as a sex check (not possible here, without an X chromosome) or as weaker associations. Changes to people go through PLINK options such as --update-sex or --keep, never through editing the .fam file.

You load PennCATH with pandas-plink's defaults and the mean of the column for rs12565286 is 1.897. The .bim file says A1 = G with a frequency of 0.0517. Is the file corrupted?

No. pandas-plink counts its a1 allele by default, which is column 6 of the .bim file, PLINK's A2 (C here). The mean count of C is \(2 - 2 \times 0.0517 = 1.897\). Pass ref="a0" to count PLINK's A1, or keep the default and record that every value counts A2.

The .bim file of one fileset lists a SNP as A/G, and another fileset lists the same rsID as T/C. Can they be merged as they are? What if one had A/T and the other T/A?

A/G and T/C are the same SNP read from opposite strands (A pairs with T, G with C), so the second fileset's letters must be complemented first, which is what --flip does in step 7. For A/T the complement is again A/T, so the letters cannot show whether the two files use the same strand; such strand-ambiguous SNPs are usually removed before a merge or resolved with allele frequencies.
