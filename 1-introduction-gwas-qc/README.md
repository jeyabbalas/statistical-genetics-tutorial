# Lecture 1 · Genetic epidemiology, GWAS and quality control

Study aid for Session 1 of the
[DCEG Statistical Genetics Workshop](https://dceg-workshops.github.io/statistical_genetics_workshop/sessions/session_1):
the lecture (slides in `../sources/lecture_1/DCEGStatGen_09sep26.pdf`), the reading
(Uffelmann et al. 2021, *Genome-wide association studies*, Nat Rev Methods Primers 1:59,
[doi:10.1038/s43586-021-00056-9](https://doi.org/10.1038/s43586-021-00056-9)) and the practical
(quality control of the PennCATH genotype data with PLINK 1.9 and GrafAnc).

This file is the authoring guide. Everyone who writes or edits a page, including an
automated agent, follows it.

## Audience and voice

Readers are data scientists and machine-learning researchers. They have no background in
genetics, biostatistics, statistical genetics or epidemiology; some are undergraduates whose
statistics is still thin. They are comfortable with code, tables, matrices, regression and
plots, and they want to see the data.

- **No analogies, metaphors or similes.** Do not write "think of LD as…", "like a barcode",
  "a fingerprint of ancestry", "the genome is a book". Say what the thing is, what is measured,
  and how it is computed. A worked number or a small table replaces an analogy.
- **Define every domain term before you use it**, in plain words, or link a Lecture 0 page that
  defines it. A term used in a sentence must already have been defined on this page, in an
  earlier sentence or a background callout, or be linked. The glossary tooltip is a backup, not
  the definition.
- **Precise and simple.** Short sentences, active voice, concrete subjects ("PLINK counts the
  missing calls for each person"). Name the unit of every number (people, SNPs, allele copies,
  pairs). Say "people" for study participants; say "sample" only for a set of people or a DNA
  specimen, and say which.
- **Statistics at the reader's level.** When a page needs a statistical idea (expected count,
  chi-square test, p-value, standard deviation, regression coefficient, principal component),
  give a one-paragraph refresher at first use, with a numeric example, or link the page that has
  it. Never assume the reader knows what "degrees of freedom" or "method of moments" means.
- **Data first.** For each concept show: how it is measured (assay, instrument, questionnaire,
  registry), what the resulting data look like (rows, columns, file, size), how it is analyzed
  (the computation, the software, the command), and what the output looks like. Real file
  excerpts and real column names beat prose.
- **Scientific care with people.** Genetic ancestry, race, ethnicity and population labels are
  different things (see `../0-biological-foundations/ancestry.html`). Ancestry assignments are
  algorithmic and relative to a reference panel. Follow the slides and the practical in saying
  so whenever ancestry groups appear.
- Use American spelling, sentence-case headings, and the en dash for ranges (slides 72–79).

## Page anatomy

Copy `_template.html`. Keep the `<head>` exactly as it is (only the title, description, widget
scripts and page styles change) and set `<body data-page="KEY">` to the page's key in
`assets/js/pages.js`. The sidebar, the table of contents, previous/next links, footer and
glossary links are generated by `site.js`; do not write them.

A page has, in order:

1. **Header**: eyebrow (`Part D · Practical · Page 15 of 23` — the number is the page's `num`
   in `pages.js`), `<h1>` equal to the page title in `pages.js`, a lede, and chips (slides
   covered, time, "Shows up in the data as").
2. **Mental model** (see below).
3. **Background callout** linking the Lecture 0 pages the reader needs (one or two sentences).
4. **Sections**, each an `<h2 id="...">` with a `Core` or `Optional` tag
   (`<span class="tag core">Core</span>`, `<span class="tag optional">Optional</span>`).
   `<h3>` for subsections. Ids are lowercase-with-hyphens and stable (other pages link to them).
5. **Key points** callout.
6. **Check your understanding**: at least five `details.q` questions with full answers that
   explain the reasoning. Mix recall, computation (with numbers) and interpretation.
7. **Learn more**: four or more curated links, each with source, level
   (`intro` / `intermediate` / `advanced`) and one line on what it adds.
8. **Sources for this page**: numbered list (`<li id="src-N">`), cited in the text as
   `<sup><a href="#src-N">N</a></sup>`. Every factual claim that is not common knowledge,
   every number from a paper, and every figure that follows a published figure has a source.

## Mental models

Every page opens with one mental model: a single sentence the reader can recall, one drawn
figure that holds the page's main ideas, and three to six hooks. Each hook names one idea and
each core section of the page develops one hook, in the same order. A mental model is a
structural summary (a pipeline, a table, a causal diagram, a matrix with labeled axes), never
an analogy. Lecture 0's pages (for example `../0-biological-foundations/haplotypes-ld.html`)
show the pattern.

The course has one overarching model that `index.html` states and every page refers back to:

> **Genetic epidemiology asks whether, how much and why genotype differences between people go
> with differences in their health. A GWAS answers it by measuring a genotype matrix
> (people × SNPs) and a phenotype vector, cleaning both, and regressing the phenotype on each
> SNP in turn while adjusting for confounders such as ancestry. Quality control decides which
> rows (people) and which columns (SNPs) of the matrix can be trusted.**

The practical has its own model, the QC pipeline: eight steps, each one "compute a statistic per
row or column → look at its distribution → choose a threshold → remove or flag → record what
was removed and why". Every QC page draws its step as one box of that pipeline.

## Terms and the glossary

`site.js` links the first use of each glossary term in each section to the glossary, with a
tooltip that shows the short definition. Lecture 0's 515 entries are loaded first; Lecture 1's
entries (built from `assets/js/glossary-parts/*.json`) are added on top.

- **Reuse Lecture 0 entries.** The id list with each entry's short definition is in the lead's
  reference file (path given in your brief) or in
  `../0-biological-foundations/assets/js/glossary-data.js`. Most terms already exist
  (genotype, allele-frequency, hwe, ld, d-prime, r-squared, pca, ibd, pi-hat, call-rate,
  missingness, plink-binary, grafanc, odds-ratio, imputation as `genotype-imputation`, …).
- **Add an entry** only for a term that is missing: write it to
  `assets/js/glossary-parts/<your-page-key>.json` (a JSON array). Before adding, search the
  existing parts (`grep -il '"id": "your-id"' assets/js/glossary-parts/*.json`) so two pages do
  not define the same term. Fields:

```json
[
  {
    "id": "exact-test",
    "term": "Exact test",
    "aka": ["exact HWE test"],
    "short": "A test whose p-value is computed from the exact probability of every possible table with the same margins, not from a large-sample approximation.",
    "long": "<p>Longer explanation (HTML). May include a worked example.</p>",
    "l1": "Slide 83 and the practical's <code>--hardy</code> output use the exact HWE test.",
    "see": ["hwe", "chi-square-test"],
    "links": [{"t": "Wigginton et al. 2005", "u": "https://doi.org/10.1086/429864"}],
    "match": ["exact test", "exact tests"],
    "owner": "frequencies-hwe"
  }
]
```

  `short` is one or two sentences of plain text (it becomes the tooltip; define the term without
  using other undefined jargon). `match` lists the strings that should become links (plurals
  are added automatically unless `"noPlural": true`; `"cs": true` makes matching
  case-sensitive, needed for acronyms such as `"HWE"`). `"auto": false` keeps an entry out of
  automatic linking. An entry with the id of a Lecture 0 entry is refused unless it has
  `"override": true`; override only when the Lecture 0 definition is wrong for this lecture.
- To link a term explicitly (for example in a place automatic linking skips), write
  `<a class="term" href="glossary.html#ID">text</a>`.
- Automatic linking skips headings, code, pre, links, buttons, figure titles, callout titles,
  widgets, labs and equation displays. Add `class="no-autolink"` to an element to skip it.
- Run `python3 1-introduction-gwas-qc/tools/build_glossary.py` after editing a part. It
  validates the entries and rebuilds `glossary-data.js`.

## Math

Follow "Writing math" in the repository's `../README.md` exactly: KaTeX, `\( \)` and `\[ \]`,
TeX commands instead of Unicode symbols, `&lt;` `&gt;` `&amp;` inside TeX, hats on estimates,
upright label subscripts, no math in headings, attributes, SVG, code or widget readouts, and
**never put a p-value in math mode** (`p` is an allele frequency). Every displayed equation sits
in an `eq-block` with **Terms** (every symbol, in reading order, with what it is counted over
and its range) and **Intuition** (why the equation has this form, extreme cases, a worked
number; no analogies). Keep display lines to about 30 characters so they fit on a phone.

Lecture 1 notation (follow the slides): allele 1 and allele 2 of a diallelic SNP; genotype
counts \(n_{11}, n_{12}, n_{22}\) with \(n = n_{11} + n_{12} + n_{22}\) people; allele frequency
\(p = p_1\), \(q = p_2 = 1 - p\); estimates \(\hat{p} = (2n_{11} + n_{12}) / (2n)\); haplotype
frequencies \(p_{11}, p_{12}, p_{21}, p_{22}\) with \(D = p_{11}p_{22} - p_{12}p_{21}\),
\(D'\) and \(r^2\). Write PLINK's names as they appear in output (PI_HAT, Z0, F_MISS, O(HOM))
in `<code>`, not math.

## Figures

- Prefer **inline SVG drawn for the lecture**: `figure.fig > .fig-body > svg` with a `viewBox`,
  `role="img"` and an `aria-label`, then `<figcaption><span class="fig-title">Title.</span> …
  <span class="fig-credit">Drawn for this lecture.</span></figcaption>`. Use the color tokens of
  `site.css` (`var(--q1)`…`var(--q8)` for categories, `--g0/--g1/--g2` for genotype 0/1/2,
  `--base-a/c/g/t`, `--mat`/`--pat`), the text classes `t`, `t-sm`, `t-xs`, `t-b`, `t-h`, and
  no text smaller than 10 px. A figure must read on a phone: give wide figures
  `class="fig scroll-x" style="--min-w: 640px"` or provide a narrow version with
  `.only-wide` / `.only-narrow`.
- Figures of **simulated data** carry a label in the caption, `<span class="illustrative">Simulated</span>`
  (site.css draws it as a small tag), and the caption says what was simulated. Figures drawn from **made-up
  numbers** (no random draws) carry `<span class="illustrative">Illustrative</span>` in the same way, and the
  caption says what the numbers are. Real data are cited.
- **Slides.** The 124 slide images are `../0-biological-foundations/assets/img/lecture1/slide-NNN.jpg`
  (three digits). Show them as thumbnails inside `callout bridge` with `loading="lazy"` and an
  `alt` that describes the slide's content in words. Decode what the slide shows; do not just
  repeat its text.
- **The reading is copyrighted** (© Springer Nature Limited 2021, not open access). Do not copy,
  crop or screenshot its figures or tables. Draw your own figure from the same information and
  credit it as "Drawn for this lecture, following Fig. N of Uffelmann et al. 2021." Quote at most
  a sentence or two, in quotation marks, with the citation.
- **Web images** only if their license allows reuse (public domain, CC BY, CC BY-SA, or a
  government work such as NHGRI or NCI images); save them under `assets/img/`, state the license
  and the author in the caption, and link the source page.
- **Check every figure visually** (see Checks). Text must not overlap other text or marks, nothing
  may be clipped by the viewBox, and labels must be readable at 375 px width.

## Widgets

A widget is an interactive figure that lets the reader change an input and see what the
statistics do. The practical needs many; the theory pages need at least one per page where a
concept has a parameter worth moving (an allele frequency, a sample size, a recombination
distance, a threshold).

- Markup on the page:

```html
<div class="widget" id="w-hwe-test">
  <div class="widget-head"><span class="badge">Try it</span><span class="wtitle">Test Hardy–Weinberg equilibrium</span></div>
  <div class="widget-body"></div>
  <noscript><div class="widget-noscript">This widget needs JavaScript. The text above describes what it shows.</div></noscript>
</div>
<p class="after-widget"><strong>What to notice.</strong> …</p>
```

- One file per widget: `assets/js/widgets/<page>-<name>.js`, loaded with
  `<script defer src="assets/js/widgets/<page>-<name>.js"></script>` after the shared scripts.
  The file is one IIFE that finds its own `div.widget` by id and fills `.widget-body`. It starts
  with a comment that states what the widget shows and the formulas it uses.
- No libraries, no modules, no network, no `fetch` of local files (so it works from `file://`).
  Draw with inline SVG or canvas. Use `site.css` widget classes: `.controls`, `.btn`,
  `.btn.primary`, `.readout`, `.note`, and the tokens above. Readouts use Unicode, not TeX.
- Simulated data must be labeled "simulated" in the widget and come from a seeded generator
  (for example mulberry32) so the first view is the same for every reader.
- Statistics must be right. Use exact formulas and well-tested numerical code (Lecture 0's
  `assets/js/widgets/allele-frequencies-hwe.js` has a chi-square tail and the exact HWE test you
  may copy). Test the numbers against a known example in Node before you rely on them.
- Widgets must work with keyboard and touch, fit a 375 px wide screen, and not overflow
  horizontally. Do not use `alert`, `confirm` or `prompt`.
- After the widget, a "What to notice" paragraph tells the reader what to try and what they
  should see.

## The lab: PLINK and R in the browser

The practical pages embed a lab: a terminal that runs a JavaScript emulation of the PLINK 1.9
commands used in the practical, plus a small Unix shell, on a **toy dataset** small enough to
ship with the page. Readers type the same commands they would type on their own computer and
get output files with the same names and columns as real PLINK. An optional R console (WebR)
runs the practical's R code on those files.

The engine lives in `assets/js/lab/`. Its exact API, markup and command list are documented in
`assets/js/lab/LAB.md` (written by the engine's author). Pages use only what LAB.md documents.

The toy dataset and its numbers:

- `data/` holds the toy files as real PLINK binary files (`toy.bed/.bim/.fam`, the reference
  panel `toy_1kg.*` and its population labels) plus `data/README.md`, the data card.
- `assets/js/lab/data-card.js` defines `window.TOY_CARD`, a flat object of named numbers
  (people, SNPs, how many fail each filter, …). Write a number from the toy data in the text as
  `<span data-card="KEY">?</span>`; `site.js` fills it in from the card, so the text always
  matches the data. Never type a toy-data number by hand.

**Real data.** Each QC page also shows the real commands for PennCATH on the reader's own
computer (paths from `setup.html`), with R code to make the practical's plots. Do not state
numerical results for the real data unless they come from the practical's own materials or a
run that was actually done; describe what to look for instead. Real PLINK 1.9.0 and GrafAnc were run
on the PennCATH files for this site in November 2026 (`scripts/qc_pipeline.sh`, then GrafAnc built from
the workshop's source); results from that run may be quoted as real PLINK's or GrafAnc's. Give a few,
so that readers can check their own run, and leave the interpretation to them. On the toy data the
lab's PLINK emulator writes the same files as real PLINK 1.9.0 (`tools/real_plink_check.mjs`).
